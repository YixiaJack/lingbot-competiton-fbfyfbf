# 决赛：训练

决赛 48 小时里，我们在一台 8 × RTX PRO 5000（72 GB）的开发机上持续训练 LingBot-VLA 2.0（6B），一个模型同时训练三个任务。现场一边采集数据一边加入训练，前后提交了三次权重。

本页讲训练怎么做的：起点、训练代码改动、数据列表怎么生成、怎么在不停训的前提下接入新数据、三次提交分别是什么。数据本身的处理见 [data.md](data.md)，最后一次提交为什么不如上一次见 [postmortem.md](postmortem.md)。

逐段的完整记录（每次启动的配置、列表、代码、步数）在 [final/training/submissions/README_third_15200.md](../../final/training/submissions/README_third_15200.md)，那是随第三轮权重一起提交的说明；本页是它的导读。

## 1. 三个阶段

步数统一用"总步数"：v2、v3 共 2000 步，v4 从 0 重新计步，**总步数 = v4 步数 + 2000**。

| 阶段 | 总步数 | 起点 | 数据 | 说明 |
|---|---|---|---|---|
| v2 | 0–1000 | 官方 LingBot-VLA 2.0 底座 | 官方 647 条示范 | 任务三按 4 个子任务切开，每段一条固定指令；任务一部分示范在头部相机上画框 |
| v3 | 1000–2000 | v2 第 1000 步 | + 自采示范和带框示范 | 打开颜色增强；**第一轮提交 = v3 第 2000 步** |
| v4 | 2000 起 | v3 第 2000 步的权重 | 每来一批新数据就重新生成列表 | 改了学习率分组，优化器状态重新开始；**第二轮 = 总 11500 步，第三轮 = 总 15200 步** |

v4 一共分了 18 段有效训练（每段一个数据列表），另有几次被替换或回退的启动，全部记在上面那份 README 的"v4 各段"表里。

## 2. 训练配置

所有 v4 配置只差数据列表（`train_path`）。

- 优化器 Muon，基础学习率 5e-5 恒定，`max_steps` 30000（按 v4 步数计；比赛在 13340 步时结束）。
- **学习率分组**（p08）：视觉塔 ×0.1，语言模型 ×0.2，动作专家和其余部分用基础学习率，官方的路由专家学习率倍数保留。底座的视觉和语言部分是在海量数据上预训练过的，我们只有几百到几千条示范，不想让它们被小数据带偏。
- 全局 batch 256（每卡 16 × 8 卡 × 梯度累积 2）。
- 颜色增强：亮度、对比度、饱和度各 ±5%（p07）。
- **训练时 RTC**（p10，总 3000 步起）：每个样本以 30% 概率不带前缀，否则把前 d 个真实动作当作已知前缀（d 在 1–24 中均匀取），loss 只算前缀之后的动作。这是为了配合推理端的异步执行 + RTC 衔接（见 [inference.md](inference.md#异步推理--rtc)），不增加参数。
- 保存间隔 500 步；最后一段为了在总 15200 步存档，改成 100 步。

## 3. 训练代码改动（p00–p10）

改动都写成可重复运行的补丁脚本，放在 [final/training/patches/](../../final/training/patches/)，打在官方训练框架上。

| 补丁 | 作用 |
|---|---|
| p00 / p02 | ViT 批量 SDPA、网格元数据缓存 |
| p01 | ViT 注意力在 sm_120（RTX PRO 5000）上改走 SDPA |
| p03 / p04 | FSDP 切分粒度与预取 |
| p05 / p06 | 融合算子、计时 |
| p07 | 颜色增强强度可配置 |
| p08 | 视觉塔 / 语言模型学习率倍数；只加载模型权重的续训方式 |
| p09 | bf16 梯度汇总 |
| p10 | 训练时 RTC（[test_p10.py](../../final/training/patches/test_p10.py) 是它的单元测试） |

速度（全局 batch 256、8 卡）：官方配置 9.83 s/步 → 批量 SDPA + 网格缓存 9.61 → 再按视觉块切 FSDP 8.67，逐步核对过 loss 一致。显式预取和编译 RMSNorm/SwiGLU 没有收益，没开。

比赛中还改过一行官方训练代码：数据列表靠重复行来加权，最长的列表有 7715 行，原代码把每行第一个词拼成一个环境变量，超过 Linux 单个环境变量 128 KB 的上限，`torch.compile` 起子进程时报 `Argument list too long`。改成去重后再拼，训练内容不变。

## 4. 数据列表：怎么决定每份数据的权重

数据加载器在列表里的所有帧上均匀采样，所以一份数据在列表里重复 n 行，被采到的概率就是 n 倍。列表由 [mk_v4c.py](../../final/training/tools/mk_v4c.py) 生成，规则如下（v4za 的实际比例见第三轮 README 的"数据配方"一节）：

- **任务比例**：任务一 : 二 : 三 = 28 : 24 : 48（按采样帧数）。任务三是双臂长程任务，给得最多。
- **任务三子任务比例**：抓取 / 扫 / 倒 / 归位 = 18 / 34 / 34 / 14。原因：第一轮评测里任务三主要失败在扫完收尾和倒，抓取全部成功；归位段长又简单，按帧均匀采样时会占 29%。
- **按采集时间加权**：越新的数据权重越高。官方数据 ×1，早期自采 ×2–3，第一天夜里采的 ×8–10，之后每来一批加 1（第 35 批为 ×35）。依据是新数据在评测工位上采，针对的是最近看到的失败。
- **人工接管数据（DAgger）**：只取推理时人工接管那一段的遥操作片段，策略自己执行的帧不用。
  - 任务一、二：同批示范的 1.5 倍，合计不超过总样本的 8%。最初设成 2 倍，有一段时间累计到 66 倍，把质量好的遥操示范压住了，后来降下来。
  - 任务三：只有人接手时所在的那个子任务算接管数据（1.5 倍），之后人完整做完的子任务按普通示范加权；另设上限，为任务三样本的 13%。
- **自采新数据整体加权**：第一天夜里起的自采批次在同一任务内整体再加 4 个百分点，从官方数据和早期数据中扣出，任务比例不变。实现时，自采新数据乘一个统一系数，其余数据分四类各乘一个系数，解方程使任务比例不变；无解时用二分查找取可行的最大加权。
- **带框数据**：每份带框数据有点名和不点名两种指令版本（例如 "Pick up the {obj} in the white box and place it on the {color} plate in the orange box."），视频和动作相同。

这套规则的问题在第三轮暴露出来：每批的权重只看采集先后、不看这一批有几条，几条示范就能占掉一个子任务的大块样本。详见 [postmortem.md](postmortem.md)。

## 5. 不停训地接入新数据

现场每隔一两个小时就有一批新数据。我们的做法是重新生成列表，然后从最近保存的 checkpoint 重启：

- 恢复模型、优化器、学习率调度和步数；换了列表的重启不恢复 dataloader 位置（`--train.resume_dataloader_state false`）。
- 这条重启路径在第一天用集群复现开发机训练时验证过：步数、学习率和 loss 都连续（[experiments/hpc_replica](../../experiments/hpc_replica/)）。

重启规则在比赛中改过两次，由 [auto_multi.sh](../../final/training/tools/auto_multi.sh) 自动执行：

1. 一开始每批到了就回到最近的存档重启。第一天晚上三次回退共丢了 432 步。
2. 改成：同时有多批等待时合并成一次重启；
3. 再改成：不回退到已经过去的存档，等训练到下一次保存完成后，带上当时所有已就绪的批次立即重启，每次只损失保存与重启之间的两三步。新批次只要在 [batches.txt](../../final/training/tools/batches.txt) 里加一行。

## 6. 存档、发布和提交

- [ckpt_guard.py](../../final/training/tools/ckpt_guard.py) 每分钟检查一次：新 checkpoint 写完 1 分钟后，把导出的 hf_ckpt 复制到 OSS，按总步数命名；磁盘不够时只清理旧存档的优化器状态，不动最新的。开发机的 pod 关掉后本地文件会丢，OSS 上的才可靠。
- 部署：在平台上把 OSS 上的 hf_ckpt 注册成技能、部署到推理机，推理机只是下载，要用 `switch.sh` 加载才算换上（见 [inference.md](inference.md)）。
- 提交包由 [make_submit.sh](../../final/training/tools/make_submit.sh) 生成：权重（SHA-256 两边核对）、训练代码、数据样例、日志和说明。推理端代码由 [collect_5080_inference.sh](../../final/training/tools/collect_5080_inference.sh) 从推理机拍快照，核对加载的权重和打包的权重一致，不含 API key。

| 轮次 | 权重 | 推理端 |
|---|---|---|
| 第一轮 | v3 第 2000 步 | 无 YOLO 框提示 |
| 第二轮 | 总 11500 步（v4 第 9500 步，列表 v4q） | YOLO v13 框提示；任务三 harness 用 11/14 晚上的版本 |
| 第三轮 | 总 15200 步（v4 第 13200 步，列表 v4za） | 同上，任务三 harness 换成带抓取检测网络的版本 |

第三轮的权重在任务三上明显不如第二轮，原因分析在 [postmortem.md](postmortem.md)。
